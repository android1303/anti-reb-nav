## 1. Мета

Автомобільний навігатор для Android, що визначає положення без GPS і без мережі (умови РЕБ) по офлайн-картах. Основа — числення шляху (Dead Reckoning): відстань зі швидкості OBD-II, курс з інтегрування гіроскопа телефона. Над ним — прив'язка до офлайн-карти (map matching) з якорями: перехрестя, кільця, мости й перепади висоти (барометр). GPS і мережева позиція — опціональні корекції й джерело автокалібрування, коли вони доступні й проходять перевірку правдоподібності; система мусить працювати без них. На етапі валідації ядра GPS — лише еталон для оцінки похибки.

Порядок обробки кожної точки в `recordPoint()` (синхронна функція, без гонок між тиками):

1. **dt** з апаратних timestamp. Нормальний крок < 1 с. Паузи потоку JS від 1 до 5 с записуються в `gapS` і доінтегровуються **лише для позиції** з останньою швидкістю (даних гіроскопа за паузу немає).
2. **LPF акселерометра** (α = 0.2).
3. **Калібрування осі руху** (для детекції реверсу) — під час розгону > 15 км/год, лише серед двох осей, що НЕ найближчі до вертикалі (вісь, найближча до вектора гравітації, віссю руху бути не може).
4. **Кутова швидкість рискання** = проєкція вектора гіроскопа на нормований вектор гравітації, × 180/π, × `YAW_SIGN`, × `GYRO_SCALE_FACTOR`. Працює за будь-якого нахилу тримача.
5. **Фільтр артефактів**: |yaw| > 150 °/с замінюється останнім валідним значенням.
6. **Машина станів:**
   - `STOPPED` — лише якщо OBD свіжий (вік ≤ 2000 мс) і швидкість = 0. Курс не інтегрується.
   - `MOVING` — OBD свіжий, швидкість > 0.
   - `OBD_LOST` — OBD застарів. Курс **продовжує** інтегруватися (поворот не можна пропустити), ZUPT не працює.
7. **ZUPT (оцінка bias гіроскопа):** перша 1 с зупинки відкидається (авто докочується; OBD показує 0 вже нижче ~2 км/год). Bias оцінюється медіаною лише після ≥ 10 с стоянки і лише якщо розкид ≤ 2.5 °/с. Оцінка зважено усереднюється з попередніми стоянками (вага = кількість зразків, максимум 2400).
8. **Інтеграція курсу** `heading += (yaw − bias_ефективний) · dt`, діапазон [0, 360), де `bias_ефективний = ZUPT_APPLY_TO_HEADING ? bias : 0` (зараз `false`: bias оцінюється й пишеться в лог, але від курсу не віднімається — див. розд. 4, п.8).
9. **Швидкість для DR:** вік OBD ≤ 2000 мс — поточна; 2000…5000 мс — остання відома (`speedExtrapolated = true`); > 5000 мс — 0.
10. **Реверс:** середнє прискорення вздовж осі руху за перші `REVERSE_WINDOW_SAMPLES` тиків (1 с) після рушання — не за одним тіком. Лише після калібрування осі (`isAxesCalibrated`); знімається на швидкості > `REVERSE_MAX_KMH` (реверс на такій швидкості неможливий).
11. **Dead Reckoning 2D:** `posX += d·sin(heading)`, `posY += d·cos(heading)`, де `d = v · (dt + gapS)`. Початковий курс 0 = напрямок авто на старті (не північ).

## 4. Незмінні правила (інваріанти)

Ці рішення прийняті на підставі даних. Змінювати їх лише за результатами аналізу нових CSV, з оновленням цього розділу.

1. Гіроскоп `expo-sensors` віддає **рад/с**; ядро працює в **°/с**.
2. **Не визначати нерухомість за акселерометром/гіроскопом.** Рух із постійною швидкістю по прямій для цих датчиків не відрізняється від стоянки. У v15 це призвело до хибного `STOPPED` на 22 км/год із замороженим курсом. Нерухомість = свіжий OBD і швидкість 0.
3. **Не пом'якшувати пороги ZUPT** (`ZUPT_MIN_SAMPLES`, `ZUPT_MAX_STD_DEG`) без перевірки відтворенням заїзду. У тесті №1 пом'якшений ZUPT збільшив похибку з 156 до 259 м.
4. Будь-яку зміну ядра перевіряти **відтворенням** записаних заїздів (подати сирі колонки CSV у `recordPoint`) і порівнювати похибку з GPS до і після.
5. У лог завжди пишуться **сирі** дані датчиків (`gyroXRaw/YRaw/ZRaw`, `speedRaw`, `obdAgeMs`, прискорення, гравітація) — інакше заїзд неможливо відтворити.
6. Під час запису нічого важкого в потоці JS (синхронізація, великі JSON) — це викликає паузи і втрату даних.
7. Збірка — лише GitHub Actions, не EAS.
8. **Bias зі стоянок не віднімається від курсу** (`ZUPT_APPLY_TO_HEADING = false`). Тести №1 і №2: bias на стоянці протилежного знаку до bias у русі; на тесті №2 застосування збільшило похибку 144.6 → 586.4 м. Вмикати лише за відтворенням, що показує покращення на всіх заїздах. Ймовірна причина: гіроскоп expo-sensors уже калібрований Android, оптимальний bias у русі ≈0 (TASK-013, розд. 7 п. 15).
9. **Вісь руху не може бути віссю, найближчою до вертикалі**; реверс визначається лише після калібрування осі, за середнім за 1 с, і не утримується понад 20 км/год.
10. **Прив'язка до карти (`geoAnchor`) не змінює `heading`/`posX`/`posY` ядра; фікси з `isMock`/`gpsMock = true` ніколи не використовуються для прив'язки** (інакше система «прив'язується» до власної підміни); **мережеві фікси використовуються лише свіжі** (вік ≤ 1500 мс, точність ≤ 300 м — `NET_MAX_ACCURACY_M`, TASK-028: фікси 400–800 м давали хибну прив'язку зі зсувом 600–800 м, 06.10), з відкиданням викидів.
11. **Підміна геолокації (`MockLocationModule`) активна лише за наявності позиції для подачі** (`geoAnchor` не в `waiting`): без неї навігатор лишається на власній геолокації, інакше він втрачає і її.

### Джерело правди

Репозиторій. Код, `docs/MASTER_PLAN.md`, `CLAUDE.md` і інструкції ролей змінюються лише комітами. Файли, завантажені в чати вручну, не є джерелом правди. Архітектор на початку кожного чату клонує публічний репозиторій https://github.com/android1303/anti-reb-nav (гілка `main`) у своєму середовищі виконання і працює лише з цією копією.

Сирі CSV заїздів у репозиторій **не комітяться**: репозиторій публічний, а CSV містять GPS-координати. Власник передає їх Архітектору вкладенням у чат; локально вони лежать у `field_tests/data/` (поза git).

CSV тесту №1 (коміт ca51b8a) лишається в історії git за рішенням Власника (23.09.2026); історія не переписується.

### Артефакти обміну

- **CSV заїзду** — Власник → Архітектор (вкладення в розмову). Локально — у `field_tests/data/`, у git не потрапляє.
- **TASK-<N>** — Архітектор → Кодер. Формат: `docs/prompts/ARCHITECT.md`. Передається без змін (Claude Code або GitHub Issue з шаблоном `task`).
- **REPORT TASK-<N>** — Кодер → Архітектор. Формат: `CLAUDE.md`.
- **Звіт заїзду** — Архітектор → `field_tests/<дата>_<назва>.md` (комітить Кодер у рамках TASK).

### Цикл

1. Заїзд за протоколом (розд. 7) → CSV.
2. Архітектор: стандартний аналіз, відтворення поточного ядра → висновки → TASK.
3. Кодер: реалізація, перевірка відтворенням (для ядра), оновлення Master Plan, коміт → REPORT.
4. Власник передає REPORT Архітектору.
5. Архітектор клонує репозиторій і перевіряє код або видає TASK-виправлення.
6. Збірка APK (GitHub Actions) → наступний заїзд.

### Рівні автоматизації

- **Рівень 1 (базовий):** TASK вставляється в локальну сесію Claude Code; коміт і push робить Кодер.
- **Рівень 2:** Claude GitHub App + Claude Code GitHub Actions. TASK публікується як GitHub Issue, коментар `@claude` запускає реалізацію й відкриває PR; Власник переглядає й зливає. Збірка APK — автоматично на push у main при зміні коду (фільтр paths у build-android.yml) або вручну (Run workflow).

### Правила обміну

- Кожна зміна поведінки — через TASK, з перевіркою і записом у Master Plan. Ручні правки коду Власником не робляться.
- «Перевірено» означає «запущено й отримано результат»; неперевірене позначається явно.
- Будь-який файл перед передачею перевіряється на версію й ключові маркери (урок v16).
- Розбіжність Кодера з TASK передається Архітектору дослівно; рішення фіксується в Master Plan.
- Посилання «розд. N» в TASK і REPORT означає відповідний файл (розд. 2 → `ARCHITECTURE.md`, 5 → `FIELD_TESTS_EARLY.md`, 7 → `TEST_PROTOCOLS.md`, 8 → `CSV_FORMAT.md`, 10 → `HISTORY.md`; розд. 0, 1, 3, 4, 6, 9 — у цьому файлі).
