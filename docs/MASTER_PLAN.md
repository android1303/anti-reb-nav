# Anti-Reb Nav — Master Plan v16

Цей документ є єдиним джерелом правди (Single Source of Truth) щодо архітектури, рішень і поточного стану проєкту Anti-Reb Nav. Він лежить у репозиторії поруч із кодом і оновлюється в тому ж коміті, що й зміни, які він описує.

Останнє оновлення: 23.09.2026, ядро телеметрії v16, після польового тесту №1; TASK-002 — структура репозиторію, Архітектор клонує репозиторій.

---

## 1. Мета

Автомобільний навігатор для Android, що визначає положення без GPS (умови РЕБ) методом числення шляху (Dead Reckoning): відстань — зі швидкості OBD-II, курс — з інтегрування гіроскопа телефона. GPS використовується лише як еталон для оцінки похибки й у розрахунках не бере участі.

## 2. Архітектура та стек

**Платформа.** React Native (Expo SDK 57), нативна збірка через GitHub Actions (`assembleRelease`) в обхід лімітів EAS; ліміт пам'яті Node `--max_old_space_size=4096`.

**Тестове середовище.** VW Jetta 2.0 (200 к.с.), полігон — Вишгород.

**Файли:**

| Файл | Призначення |
|---|---|
| `Elm327Module.kt` | Нативний Bluetooth-модуль ELM327. RFCOMM через рефлексію (`createRfcommSocket`) в обхід IOException на Android 13+. Потік читання додає до кожної порції даних апаратний timestamp. |
| `obdScanner.js` | Ініціалізація ELM327, опитування швидкості (PID `010D`), парсинг. |
| `telemetry.js` | Ядро: машина станів, ZUPT, курс, Dead Reckoning, локальне зберігання, синхронізація, офлайн-експорт CSV. |
| `exportService.js` | Експорт з Firestore у CSV (новий формат порцій + legacy). |
| `App.js` | UI, підписки на датчики, цикл ядра 20 Гц, keep-awake під час запису. |
| `tools/replay/replay.mjs` | Відтворення заїзду: сирі колонки CSV → справжнє ядро `telemetry.js` (Node + esbuild). |
| `tools/replay/compare.py` | Порівняння траєкторії DR з GPS за методикою розд. 5 (похибка, RMS, м/км, графік). |

**Датчики (20 Гц / 50 мс):**

- Швидкість — OBD-II через ELM327. Опитування за схемою «запит → відповідь `>` → наступний запит» (пауза 50 мс); фактичне оновлення в тесті №1 — медіана 91 мс.
- Гіроскоп — `expo-sensors`, **одиниці рад/с** (конвертація в °/с робиться в ядрі).
- DeviceMotion — лінійне прискорення та вектор гравітації (`accelerationIncludingGravity − acceleration`).
- Барометр — 1 Гц, відносна висота `(p0 − p) × 8.3 м/гПа`.
- GPS — лише еталон (ground truth).

**Зберігання та експорт:**

- Точки накопичуються в пам'яті й кожні 5 с скидаються порцією у файл `documentDirectory/telemetry/pending/<startTs>_<sessionId>_<count>.json` (без ліміту AsyncStorage — важливо для довгих офлайн-заїздів).
- Синхронізація: одна порція = один документ у колекції Firestore `telemetry_chunks`. Після успіху файл переміщується в `synced/`.
- **Під час запису синхронізація вимкнена** (блокувала потік JS); запускається автоматично після `stopSession()`.
- Експорт CSV: звичайне натискання — з локальних файлів (офлайн); довге — з Firestore. Обидва шляхи використовують один список колонок `CSV_COLUMNS`.
- Стара колекція `telemetry_logs` (1 документ = 1 точка, до v14) експортується лише через `exportLegacyLogsToCSV` у старому форматі; змішувати зі новими даними не можна (там `gyroZ` уже очищений і в рад/с).

## 3. Ядро навігації (telemetry.js v16)

Порядок обробки кожної точки в `recordPoint()` (синхронна функція, без гонок між тиками):

1. **dt** з апаратних timestamp. Нормальний крок < 1 с. Паузи потоку JS від 1 до 5 с записуються в `gapS` і доінтегровуються **лише для позиції** з останньою швидкістю (даних гіроскопа за паузу немає).
2. **LPF акселерометра** (α = 0.2).
3. **Калібрування осі руху** (для детекції реверсу) — під час розгону > 15 км/год.
4. **Кутова швидкість рискання** = проєкція вектора гіроскопа на нормований вектор гравітації, × 180/π, × `YAW_SIGN`, × `GYRO_SCALE_FACTOR`. Працює за будь-якого нахилу тримача.
5. **Фільтр артефактів**: |yaw| > 150 °/с замінюється останнім валідним значенням.
6. **Машина станів:**
   - `STOPPED` — лише якщо OBD свіжий (вік ≤ 2000 мс) і швидкість = 0. Курс не інтегрується.
   - `MOVING` — OBD свіжий, швидкість > 0.
   - `OBD_LOST` — OBD застарів. Курс **продовжує** інтегруватися (поворот не можна пропустити), ZUPT не працює.
7. **ZUPT (оцінка bias гіроскопа):** перша 1 с зупинки відкидається (авто докочується; OBD показує 0 вже нижче ~2 км/год). Bias оцінюється медіаною лише після ≥ 10 с стоянки і лише якщо розкид ≤ 2.5 °/с. Оцінка зважено усереднюється з попередніми стоянками (вага = кількість зразків, максимум 2400).
8. **Інтеграція курсу** `heading += (yaw − bias) · dt`, діапазон [0, 360).
9. **Швидкість для DR:** вік OBD ≤ 2000 мс — поточна; 2000…5000 мс — остання відома (`speedExtrapolated = true`); > 5000 мс — 0.
10. **Реверс** визначається в момент рушання за знаком прискорення вздовж осі руху.
11. **Dead Reckoning 2D:** `posX += d·sin(heading)`, `posY += d·cos(heading)`, де `d = v · (dt + gapS)`. Початковий курс 0 = напрямок авто на старті (не північ).

| Константа | Значення | Статус / обґрунтування |

## 4. Незмінні правила (інваріанти)

Ці рішення прийняті на підставі даних. Змінювати їх лише за результатами аналізу нових CSV, з оновленням цього розділу.

1. Гіроскоп `expo-sensors` віддає **рад/с**; ядро працює в **°/с**.
2. **Не визначати нерухомість за акселерометром/гіроскопом.** Рух із постійною швидкістю по прямій для цих датчиків не відрізняється від стоянки. У v15 це призвело до хибного `STOPPED` на 22 км/год із замороженим курсом. Нерухомість = свіжий OBD і швидкість 0.
3. **Не пом'якшувати пороги ZUPT** (`ZUPT_MIN_SAMPLES`, `ZUPT_MAX_STD_DEG`) без перевірки відтворенням заїзду. У тесті №1 пом'якшений ZUPT збільшив похибку з 156 до 259 м.
4. Будь-яку зміну ядра перевіряти **відтворенням** записаних заїздів (подати сирі колонки CSV у `recordPoint`) і порівнювати похибку з GPS до і після.
5. У лог завжди пишуться **сирі** дані датчиків (`gyroXRaw/YRaw/ZRaw`, `speedRaw`, `obdAgeMs`, прискорення, гравітація) — інакше заїзд неможливо відтворити.
6. Під час запису нічого важкого в потоці JS (синхронізація, великі JSON) — це викликає паузи і втрату даних.
7. Збірка — лише GitHub Actions, не EAS.

## 5. Польовий тест №1 (23.09.2026, Вишгород)

**Умови:** 4 хв 16 с, 1.38 км за GPS. Маршрут: ~370 м на південь, два ліві повороти по 90° провулком, ~1 км на північ. Телефон у тримачі вертикально, нахил ~17° назад. Ядро v15 (під час заїзду), відтворення через v16.

**Методика:** траєкторія DR вирівнюється з GPS за першими 280 м прямої (відомі старт і напрямок — реалістичний сценарій РЕБ), далі — лише датчики.

**Результати:**

| Показник | Значення |
|---|---|
| Похибка після 373 м (з обома поворотами) | 8 м |
| Кінцева похибка, v15 (як записано) | 168 м на 1.38 км (~12%) |
| Кінцева похибка, відтворення v16 | 156 м |
| Кінцева похибка з постійним bias −0.07 °/с (теоретична межа) | ~23 м (~1.7%) |
| Точність відстані за OBD | 98–100% на відрізках |
| Похибка курсу після 180° поворотів | 2–3° |
| Шум гіроскопа в русі / на стоянці | 2.4 °/с / 1.0–1.7 °/с |
| Оновлення OBD | медіана 91 мс, 99-й перцентиль 242 мс |

**Виявлені проблеми:**

1. **Паузи потоку JS кожні ~30 с** (0.13–0.23 с, одна — 2.6 с) через синхронізацію з Firestore. Пауза 2.6 с «з'їла» ~16 м траєкторії. *Виправлено у v16* (синхронізація після запису, доінтегрування пауз).
2. **ZUPT не спрацював жодного разу** (поріг 0.5 °/с при реальному розкиді 0.56–2.2). *Виправлено у v16*, але див. гіпотезу нижче.
3. **Дрейф курсу** на північному відрізку: похибка зростає з −2° до −16° на прямій дорозі. Головне джерело кінцевої похибки.
4. **Чутливість до bias:** 0.1 °/с помилки bias = 100–200 м на цьому маршруті. Потрібна точність ±0.02 °/с.
5. **Логіка v15 при втраті OBD** (хибний `STOPPED`, мертва умова екстраполяції). *Виправлено у v16.*
6. **Запис обірвався на 26 км/год** — ймовірно, телефон заснув. *Виправлено: keep-awake під час запису.*
7. **GPS-еталон розріджений** — оновлення кожні 5–7 с (~55 м).

**Відкрита гіпотеза (головне питання тесту №2):** дві «чисті» стоянки показали bias +0.08…+0.13 °/с, а оптимальний bias у русі — близько −0.07 °/с (протилежний знак). Якщо bias на стоянці не збігається з bias у русі (вібрація, температура, g-чутливість MEMS), ZUPT на цьому телефоні не дасть очікуваного ефекту і знадобиться інший підхід до компенсації дрейфу.

## 8. Формат CSV (колонки `CSV_COLUMNS`)

### Джерело правди

Репозиторій. Код, `docs/MASTER_PLAN.md`, `CLAUDE.md` і інструкції ролей змінюються лише комітами. Файли, завантажені в чати вручну, не є джерелом правди. Архітектор на початку кожного чату клонує публічний репозиторій https://github.com/android1303/anti-reb-nav (гілка `main`) у своєму середовищі виконання і працює лише з цією копією.

Сирі CSV заїздів у репозиторій **не комітяться**: репозиторій публічний, а CSV містять GPS-координати. Власник передає їх Архітектору вкладенням у чат; локально вони лежать у `field_tests/data/` (поза git).

### Артефакти обміну

- **CSV заїзду** — Власник → Архітектор (вкладення в розмову). Локально — у `field_tests/data/`, у git не потрапляє.
- **TASK-<N>** — Архітектор → Кодер. Формат: `docs/prompts/ARCHITECT.md`. Передається без змін (Claude Code або GitHub Issue з шаблоном `task`).
- **REPORT TASK-<N>** — Кодер → Архітектор. Формат: `CLAUDE.md`.
- **Звіт заїзду** — Архітектор → `field_tests/<дата>_<назва>.md` (комітить Кодер у рамках TASK).

### Цикл

1. Заїзд за протоколом (розд. 7) → CSV.
2. Архітектор: стандартний аналіз, відтворення поточного ядра → висновки → TASK.
3. Кодер: реалізація, перевірка відтворенням (для ядра), оновлення Master Plan, коміт → REPORT.
4. Власник передає REPORT Архітектору.
5. Архітектор клонує репозиторій і перевіряє код або видає TASK-виправлення.
6. Збірка APK (GitHub Actions) → наступний заїзд.

### Рівні автоматизації

- **Рівень 1 (базовий):** TASK вставляється в локальну сесію Claude Code; коміт і push робить Кодер.
- **Рівень 2:** Claude GitHub App + Claude Code GitHub Actions. TASK публікується як GitHub Issue, коментар `@claude` запускає реалізацію й відкриває PR; Власник переглядає й зливає. Збірка APK — на push у `main`.

### Правила обміну

- Кожна зміна поведінки — через TASK, з перевіркою і записом у Master Plan. Ручні правки коду Власником не робляться.
- «Перевірено» означає «запущено й отримано результат»; неперевірене позначається явно.
- Будь-який файл перед передачею перевіряється на версію й ключові маркери (урок v16).
- Розбіжність Кодера з TASK передається Архітектору дослівно; рішення фіксується в Master Plan.
