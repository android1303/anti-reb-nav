# Anti-Reb Nav — Master Plan v17

Цей документ є єдиним джерелом правди (Single Source of Truth) щодо архітектури, рішень і поточного стану проєкту Anti-Reb Nav. Він лежить у репозиторії поруч із кодом і оновлюється в тому ж коміті, що й зміни, які він описує.

Останнє оновлення: 03.10.2026, ядро телеметрії v21 (TASK-017: некалібрований гіроскоп у лозі паралельно; розрахунок без змін).

---

## 1. Мета

Автомобільний навігатор для Android, що визначає положення без GPS і без мережі (умови РЕБ) по офлайн-картах. Основа — числення шляху (Dead Reckoning): відстань зі швидкості OBD-II, курс з інтегрування гіроскопа телефона. Над ним — прив'язка до офлайн-карти (map matching) з якорями: перехрестя, кільця, мости й перепади висоти (барометр). GPS і мережева позиція — опціональні корекції й джерело автокалібрування, коли вони доступні й проходять перевірку правдоподібності; система мусить працювати без них. На етапі валідації ядра GPS — лише еталон для оцінки похибки.

## 2. Архітектура та стек

**Платформа.** React Native (Expo SDK 57), нативна збірка через GitHub Actions (`assembleRelease`) в обхід лімітів EAS; ліміт пам'яті Node `--max_old_space_size=4096`.

**Тестове середовище.** VW Jetta 2.0 (200 к.с.), полігон — Вишгород.

**Файли:**

**Датчики (20 Гц / 50 мс):**

- Швидкість — OBD-II через ELM327. Опитування за схемою «запит → відповідь `>` → наступний запит» (пауза 50 мс); фактичне оновлення в тесті №1 — медіана 91 мс.
- Гіроскоп — **одиниці рад/с** (конвертація в °/с робиться в ядрі). З TASK-016 входи ядра (гіроскоп, лінійне прискорення, гравітація) беруть з нативного `SensorModule` (працює у фоні); `expo-sensors` лишаються паралельним записом (`gyroXRaw`…, `accelX`…, `gravX`…; порожньо, коли застосунок у фоні) для перевірки еквівалентності. Якщо нативні значення відсутні — ядро бере expo, як до v20 (`sensorSource`).
- DeviceMotion (expo) — лінійне прискорення та вектор гравітації (`accelerationIncludingGravity − acceleration`; expo рахує `accelerationIncludingGravity = TYPE_ACCELEROMETER − 2·TYPE_GRAVITY`, тож `gravX/Y/Z` ≈ −`TYPE_GRAVITY`). Нативний аналог — `SensorModule` (див. вище).
- Барометр — 1 Гц, відносна висота `(p0 − p) × 8.3 м/гПа`.
- GPS — лише еталон (ground truth). З TASK-012 — нативний `GnssModule` напряму: `GPS_PROVIDER` (чистий GNSS-приймач, 1 с, 0 м) окремо від `NETWORK_PROVIDER` (мережева позиція) і `GnssStatus`; fused-провайдер Google через `Location.watchPositionAsync` (`Accuracy.BestForNavigation`) більше не використовується як еталон: він не повідомляє джерело позиції (мережева позиція з точністю 5–8 м за полями лога не відрізняється від GPS), а при вимкненій «Точній геолокації» показує системний діалог і після відмови кидає помилку — еталон не вмикався взагалі. `lat`/`lon`/`gpsAccuracy` у лозі означають лише GPS-приймач і тримаються між фіксами (зміна `lat`/`lon` = нова точка для `compare.py`); вік фіксу — `gpsFixAgeMs`. Fused тепер пишеться окремо (`fused*`, TASK-013) — лише для визначення джерела позиції під час глушіння, у розрахунку й еталоні не бере участі. Дозвіл запитується через `Location.requestForegroundPermissionsAsync`. (Історія: до TASK-006 дефолтний `distanceInterval = 50` м для `Accuracy.High`; TASK-006 — `BestForNavigation`/1 с/`distanceInterval: 0`.)

**Робота у фоні й з вимкненим екраном (TASK-016).** Таймери JS у React Native (`JavaTimerManager`) прив'язані до Choreographer і призупиняються у фоні (`onHostPause`); Headless JS їх лише розморожує, але все одно через Choreographer, який з вимкненим екраном (немає vsync) ненадійний. Тому обрано нативний такт: окремий потік `SensorModule` шле подію `nativeSensors` кожні 50 мс (`postAtTime` без накопичення дрейфу), і саме від неї працюють (1) цикл ядра 20 Гц (`recordPoint`; `timestamp` = нативний `System.currentTimeMillis`), (2) таймери OBD-опитування, (3) flush логу — через `bgScheduler.js`. Якщо нативних тактів немає (> 200 мс), працює запасний `setInterval` 50 мс. `RecordingService` тримає процес живим, показує сповіщення і `PARTIAL_WAKE_LOCK`; запускається/зупиняється кнопкою запису (на Android 13+ при першому старті запитується `POST_NOTIFICATIONS`). Headless JS не використовується.

**Зберігання та експорт:**

- Точки накопичуються в пам'яті й кожні 5 с скидаються порцією у файл `documentDirectory/telemetry/pending/<startTs>_<sessionId>_<count>.json` (без ліміту AsyncStorage — важливо для довгих офлайн-заїздів).
- Синхронізація: одна порція = один документ у колекції Firestore `telemetry_chunks`. Після успіху файл переміщується в `synced/`.
- **Під час запису синхронізація вимкнена** (блокувала потік JS); запускається автоматично після `stopSession()`. UI показує правдивий стан (`getSyncState()`: `isSyncing`, `isRecording`, `lastSyncAt`, `lastSyncResult`) — кнопка й час «Синхр:» відображають і фонову синхронізацію після запису, а не лише ручне натискання (TASK-006).
- Експорт CSV: звичайне натискання — вибір сесії (Alert: «Остання сесія» / «Усі сесії» / «Скасувати», `telemetry.getLastSessionId()`) з локальних файлів (офлайн); довге — з Firestore, завжди всі сесії. Обидва шляхи використовують один список колонок `CSV_COLUMNS`. Назва локального файлу: `anti_reb_<sessionId|all>_<Date.now()>_<CORE_VERSION>.csv` — версія ядра видна без відкриття файлу.
- Стара колекція `telemetry_logs` (1 документ = 1 точка, до v14) експортується лише через `exportLegacyLogsToCSV` у старому форматі; змішувати зі новими даними не можна (там `gyroZ` уже очищений і в рад/с).

## 3. Ядро навігації (telemetry.js v21)

v18 (TASK-012) і v19 (TASK-013) змінили лише формат лога (колонки GNSS, мережі та fused; `lat`/`lon`/`gpsAccuracy` = лише GPS-приймач). v21 (TASK-017) лише додав колонки некаліброваного гіроскопа; ядро їх не використовує (відтворення тесту №5 ядром v21 ідентичне v20). v20 (TASK-016) змінив джерело входів (нативні датчики, якщо вони є; інакше expo) і додав колонки; **математика без змін**: відтворення тестів №1, №2 (пряма), №4, №5 ядром v18, v19 і v20 (старі CSV без нативних колонок -> вхід expo) дає побітово ті самі `posX`/`posY`/`heading`, що v17 (тест №5: кінцева 10.4 м, RMS 14.1 м, 7 м/км).

Порядок обробки кожної точки в `recordPoint()` (синхронна функція, без гонок між тиками):

1. **dt** з апаратних timestamp. Нормальний крок < 1 с. Паузи потоку JS від 1 до 5 с записуються в `gapS` і доінтегровуються **лише для позиції** з останньою швидкістю (даних гіроскопа за паузу немає).
2. **LPF акселерометра** (α = 0.2).
3. **Калібрування осі руху** (для детекції реверсу) — під час розгону > 15 км/год, лише серед двох осей, що НЕ найближчі до вертикалі (вісь, найближча до вектора гравітації, віссю руху бути не може).
4. **Кутова швидкість рискання** = проєкція вектора гіроскопа на нормований вектор гравітації, × 180/π, × `YAW_SIGN`, × `GYRO_SCALE_FACTOR`. Працює за будь-якого нахилу тримача.
5. **Фільтр артефактів**: |yaw| > 150 °/с замінюється останнім валідним значенням.
6. **Машина станів:**
   - `STOPPED` — лише якщо OBD свіжий (вік ≤ 2000 мс) і швидкість = 0. Курс не інтегрується.
   - `MOVING` — OBD свіжий, швидкість > 0.
   - `OBD_LOST` — OBD застарів. Курс **продовжує** інтегруватися (поворот не можна пропустити), ZUPT не працює.
7. **ZUPT (оцінка bias гіроскопа):** перша 1 с зупинки відкидається (авто докочується; OBD показує 0 вже нижче ~2 км/год). Bias оцінюється медіаною лише після ≥ 10 с стоянки і лише якщо розкид ≤ 2.5 °/с. Оцінка зважено усереднюється з попередніми стоянками (вага = кількість зразків, максимум 2400).
8. **Інтеграція курсу** `heading += (yaw − bias_ефективний) · dt`, діапазон [0, 360), де `bias_ефективний = ZUPT_APPLY_TO_HEADING ? bias : 0` (зараз `false`: bias оцінюється й пишеться в лог, але від курсу не віднімається — див. розд. 4, п.8).
9. **Швидкість для DR:** вік OBD ≤ 2000 мс — поточна; 2000…5000 мс — остання відома (`speedExtrapolated = true`); > 5000 мс — 0.
10. **Реверс:** середнє прискорення вздовж осі руху за перші `REVERSE_WINDOW_SAMPLES` тиків (1 с) після рушання — не за одним тіком. Лише після калібрування осі (`isAxesCalibrated`); знімається на швидкості > `REVERSE_MAX_KMH` (реверс на такій швидкості неможливий).
11. **Dead Reckoning 2D:** `posX += d·sin(heading)`, `posY += d·cos(heading)`, де `d = v · (dt + gapS)`. Початковий курс 0 = напрямок авто на старті (не північ).

## 4. Незмінні правила (інваріанти)

Ці рішення прийняті на підставі даних. Змінювати їх лише за результатами аналізу нових CSV, з оновленням цього розділу.

1. Гіроскоп `expo-sensors` віддає **рад/с**; ядро працює в **°/с**.
2. **Не визначати нерухомість за акселерометром/гіроскопом.** Рух із постійною швидкістю по прямій для цих датчиків не відрізняється від стоянки. У v15 це призвело до хибного `STOPPED` на 22 км/год із замороженим курсом. Нерухомість = свіжий OBD і швидкість 0.
3. **Не пом'якшувати пороги ZUPT** (`ZUPT_MIN_SAMPLES`, `ZUPT_MAX_STD_DEG`) без перевірки відтворенням заїзду. У тесті №1 пом'якшений ZUPT збільшив похибку з 156 до 259 м.
4. Будь-яку зміну ядра перевіряти **відтворенням** записаних заїздів (подати сирі колонки CSV у `recordPoint`) і порівнювати похибку з GPS до і після.
5. У лог завжди пишуться **сирі** дані датчиків (`gyroXRaw/YRaw/ZRaw`, `speedRaw`, `obdAgeMs`, прискорення, гравітація) — інакше заїзд неможливо відтворити.
6. Під час запису нічого важкого в потоці JS (синхронізація, великі JSON) — це викликає паузи і втрату даних.
7. Збірка — лише GitHub Actions, не EAS.
8. **Bias зі стоянок не віднімається від курсу** (`ZUPT_APPLY_TO_HEADING = false`). Тести №1 і №2: bias на стоянці протилежного знаку до bias у русі; на тесті №2 застосування збільшило похибку 144.6 → 586.4 м. Вмикати лише за відтворенням, що показує покращення на всіх заїздах. Ймовірна причина: гіроскоп expo-sensors уже калібрований Android, оптимальний bias у русі ≈0 (TASK-013, розд. 7 п. 15).
9. **Вісь руху не може бути віссю, найближчою до вертикалі**; реверс визначається лише після калібрування осі, за середнім за 1 с, і не утримується понад 20 км/год.

## 5. Польовий тест №1 (23.09.2026, Вишгород)

**Умови:** 4 хв 16 с, 1.38 км за GPS. Маршрут: ~370 м на південь, два ліві повороти по 90° провулком, ~1 км на північ. Телефон у тримачі вертикально, нахил ~17° назад. Ядро v15 (під час заїзду), відтворення через v16.

**Методика:** траєкторія DR вирівнюється з GPS за першими 280 м прямої (відомі старт і напрямок — реалістичний сценарій РЕБ), далі — лише датчики.

2. **60 с стоянки із заведеним двигуном, нічого не торкаючись** — дані для bias і шуму.
3. Маршрут 3–6 км, по можливості замкнений (фініш у точці старту — еталон і без GPS): повороти в обидва боки (≥ 3 праворуч і ≥ 3 ліворуч), кільце (якщо є поруч), міст/естакада або помітний підйом, пряма ≥ 1 км.
4. Щонайменше 3 стоянки по 15–20 с із заведеним двигуном (поріг ZUPT ≈ 11 с), нічого не торкаючись.
5. Вентиляцію, кондиціонер і вікна не змінювати протягом заїзду (барометр).
6. Наприкінці — 30–60 с стоянки, потім зупинити запис кнопкою.
7. Експорт CSV (офлайн) → на аналіз Архітектору; окремо записати: марка/модель авто, модель телефона, чи був інтернет.
8. Фіксувати рівень тривоги/підозру на РЕБ в описі заїзду (тест №4: жовтий рівень тривоги співпав з різким погіршенням GPS — гіпотеза не підтверджена й не спростована одним заїздом).

### Протокол тесту №3

Як у протоколі тесту №2, плюс:

(а) Справжній задній хід 10–15 м зі стоянки (перевірка спрацювання детектора реверсу v17).
(б) Той самий квартал в обидва напрямки — і праві, і ліві повороти (розділити масштаб курсу й bias, див. розд. 5).
(в) Одна зі стоянок — 60 с із **заглушеним двигуном** (чи зникає розбіжність bias «стоянка проти руху» без вібрації двигуна).

### Джерело правди

Репозиторій. Код, `docs/MASTER_PLAN.md`, `CLAUDE.md` і інструкції ролей змінюються лише комітами. Файли, завантажені в чати вручну, не є джерелом правди. Архітектор на початку кожного чату клонує публічний репозиторій https://github.com/android1303/anti-reb-nav (гілка `main`) у своєму середовищі виконання і працює лише з цією копією.

Сирі CSV заїздів у репозиторій **не комітяться**: репозиторій публічний, а CSV містять GPS-координати. Власник передає їх Архітектору вкладенням у чат; локально вони лежать у `field_tests/data/` (поза git).

CSV тесту №1 (коміт ca51b8a) лишається в історії git за рішенням Власника (23.09.2026); історія не переписується.

### Артефакти обміну

- **CSV заїзду** — Власник → Архітектор (вкладення в розмову). Локально — у `field_tests/data/`, у git не потрапляє.
- **TASK-<N>** — Архітектор → Кодер. Формат: `docs/prompts/ARCHITECT.md`. Передається без змін (Claude Code або GitHub Issue з шаблоном `task`).
- **REPORT TASK-<N>** — Кодер → Архітектор. Формат: `CLAUDE.md`.
- **Звіт заїзду** — Архітектор → `field_tests/<дата>_<назва>.md` (комітить Кодер у рамках TASK).

### Цикл

1. Заїзд за протоколом (розд. 7) → CSV.
2. Архітектор: стандартний аналіз, відтворення поточного ядра → висновки → TASK.
3. Кодер: реалізація, перевірка відтворенням (для ядра), оновлення Master Plan, коміт → REPORT.
4. Власник передає REPORT Архітектору.
5. Архітектор клонує репозиторій і перевіряє код або видає TASK-виправлення.
6. Збірка APK (GitHub Actions) → наступний заїзд.

### Рівні автоматизації

- **Рівень 1 (базовий):** TASK вставляється в локальну сесію Claude Code; коміт і push робить Кодер.
- **Рівень 2:** Claude GitHub App + Claude Code GitHub Actions. TASK публікується як GitHub Issue, коментар `@claude` запускає реалізацію й відкриває PR; Власник переглядає й зливає. Збірка APK — автоматично на push у main при зміні коду (фільтр paths у build-android.yml) або вручну (Run workflow).

### Правила обміну

- Кожна зміна поведінки — через TASK, з перевіркою і записом у Master Plan. Ручні правки коду Власником не робляться.
- «Перевірено» означає «запущено й отримано результат»; неперевірене позначається явно.
- Будь-який файл перед передачею перевіряється на версію й ключові маркери (урок v16).
- Розбіжність Кодера з TASK передається Архітектору дослівно; рішення фіксується в Master Plan.
